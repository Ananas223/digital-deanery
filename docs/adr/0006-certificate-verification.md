# ADR 0006. Печатная справка и публичная проверка по QR

| Поле      | Значение                                            |
| --------- | --------------------------------------------------- |
| Статус    | Принято                                             |
| Дата      | 22.11.2026                                          |
| Контекст  | `Ф-04.10`, `US-15`, `A-16`, `P10-IDEA-02`           |
| Связанные | [`SPEC-P4-REQUESTS`](../specs/p4-requests.md) § 4.6 |
| Заменяет  | —                                                   |

## Контекст

Готовая справка об обучении или справке по месту требования должна выглядеть как документ, который можно распечатать, и при этом не выдавать себя за официальный документ вуза. Получателю нужно убедиться, что бланк выпущен учебным концептом и относится к указанному студенту, не входя в кабинет и не получая лишних персональных данных.

PDF-генератор отклонён ранее: тяжёлая зависимость ради одной кнопки, достаточно печати HTML (`P10-C`). Публичная подписка и внешние сервисы QR тоже не подходят: новый публичный контракт и утечка URL во внешнюю систему.

## Рассмотренные варианты

| Вариант                        | Плюсы                                      | Минусы                                                                                           |
| ------------------------------ | ------------------------------------------ | ------------------------------------------------------------------------------------------------ |
| Код = `id` или номер заявки    | Просто                                     | Перебираемый и связанный с внутренним идентификатором; раскрывает существование заявки           |
| Подписанный токен (HMAC от id) | Нет хранения                               | Нужен секрет и стабильный формат; при утечке секрета компрометируются все коды; сложнее отозвать |
| Случайный код в отдельном поле | Неперебираемый, отзываемый, не связан с id | Нужна миграция и уникальный индекс                                                               |
| Внешний сервис QR              | Ноль кода                                  | Внешняя зависимость и передача URL третьей стороне                                               |

## Решение

1. `Request.verifyCode String? @unique` — новые коды: 12 случайных байт (`crypto.randomBytes(12).toString("base64url")`, 16 символов, 96 бит). Код выдаётся при создании заявки типов `STUDY_CERTIFICATE` и `PLACE_REQUIREMENT`; для остальных типов остаётся `null`. Коллизия разрешается повторной генерацией при `P2002`, не более трёх попыток. Существующие строки при миграции получают `gen_random_uuid()::text` (122 бита).
2. Печатный бланк — `GET /requests/[id]/print`, только владелец, только `READY`, только типы справок. Домен отдаёт `getCertificateForOwner(userId, requestId)`, который не переиспользует `getRequest` (тот скрывает данные студента от студента).
3. Публичная проверка — `GET /verify/[code]` без сессии. Домен `getCertificateVerification(code)` возвращает только ФИО, факультет, направление, курс, группу, дату готовности и статус. Неизвестный код, не-`READY` и не-справочный тип дают одинаковый нейтральный `notFound()`.
4. `proxy.ts` пропускает `/verify` без cookie; страница сама решает, что показать. Proxy остаётся грубым фильтром, а не авторизацией.
5. QR строится на сервере пакетом `qrcode` (MIT) в PNG data URL. Содержимое — `${NEXT_PUBLIC_APP_URL}/verify/${verifyCode}`; заголовок `Host` не используется. Пакет фиксируется в `docs/third-party.md`.
6. Оба маршрута динамические, `Cache-Control: no-store`. `verifyCode` не попадает в списки и карточки заявок, логи и публичные проекции.
7. Бланк содержит водяной знак «КОНЦЕПТ · НЕ ОФИЦИАЛЬНЫЙ ДОКУМЕНТ» и пометку о конкурсном концепте; официальная символика вуза не используется.

## Последствия

- Нужна миграция с nullable-полем и уникальным индексом; существующие строки получают код через `gen_random_uuid()`.
- Seed создаёт детерминированные демонстрационные коды для готовых справок, чтобы повторный запуск был идемпотентным.
- Проверка не раскрывает номер заявки, номер студенческого, e-mail, payload и историю.
- 96 бит энтропии делают перебор нецелесообразным; отдельный rate limit для `/verify` не требуется.
- Отзыв кода — смена `verifyCode` или статуса заявки; старая ссылка перестаёт находить документ.
- Тесты: юнит на формат кода, интеграционные на владельца/чужого/статус/минимум полей, E2E на печать и гостевую проверку.
