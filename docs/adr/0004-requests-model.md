# ADR 0004. Модель заявок и история статусов

| Поле                | Значение                                                                                                                    |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Статус              | Принято                                                                                                                     |
| Дата                | 17.11.2026                                                                                                                  |
| Контекст            | Этап 4, задачи `P4-BE-01`–`P4-BE-05`; требования `Ф-04`, `US-06`–`US-08` в `docs/PRD.md`                                    |
| Связанные документы | [`docs/specs/p4-requests.md`](../specs/p4-requests.md), `docs/PRD.md`, `docs/DEVELOPMENT_PLAN.md`, `AGENTS.md` § 2.4, § 3.2 |

## Контекст

Студент создаёт заявку одного из четырёх типов, видит номер, дату, статус и историю, может отменить заявку только в статусе `NEW`. Сотрудник деканата переводит заявку в работу, завершает или отклоняет с обязательной причиной; смена статуса создаёт уведомление. Требования и сценарии описаны в `Ф-04`, `US-06`–`US-08`; детальный контракт — в [`docs/specs/p4-requests.md`](../specs/p4-requests.md).

Модель должна одновременно поддержать: разные наборы полей у четырёх типов, неизменяемую историю переходов, проверку допустимости перехода на сервере, выдачу только своих заявок студенту и очередь сотруднику. Формат номера, состав полей типов, статус `CANCELLED`, идемпотентность и поведение уведомления при сбое согласованы владельцем продукта 17.11.2026 и зафиксированы в спецификации; ADR фиксирует архитектурный выбор под эти решения.

## Рассмотренные варианты

| Вариант                                                              | Сущности                                                                                               | Плюсы                                                                                                               | Минусы                                                                                                                       |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Одна таблица `Request` + `payload` JSON + справочник типов + история | `RequestType`, `Request`, `RequestStatusHistory`                                                       | Один список, фильтры и переходы для всех типов; новый тип — запись справочника и Zod-схема; история в одной таблице | Поля `payload` не проверяются базой; нужна Zod-валидация на каждой записи и чтении                                           |
| Отдельная таблица на каждый тип                                      | `StudyCertificateRequest`, `PlaceRequirementRequest`, `AcademicLeaveRequest`, `RetakeRequest`, история | Строгие колонки и ограничения для каждого типа                                                                      | Дублирование списка, статусов, истории и прав; общий экран и очередь требуют объединения через `UNION`; новый тип — миграция |
| Одна широкая таблица со всеми полями типов                           | `Request` с nullable-колонками под каждый тип                                                          | Простые запросы без JSON                                                                                            | Много пустых колонок, правила «какие поля обязательны» живут только в коде, добавление типа меняет схему                     |

## Решение

Принять первый вариант: **одна заявка, справочник типов, JSON-полезная нагрузка и отдельная история статусов**.

### Сущности

- `RequestType` — тип заявки: `code` (уникальный), название, описание, срок обработки в днях, признак активности, порядок вывода. Коды: `STUDY_CERTIFICATE`, `PLACE_REQUIREMENT`, `ACADEMIC_LEAVE`, `RETAKE`.
- `Request` — заявка студента: уникальный номер, ссылка на `StudentProfile`, ссылка на `RequestType`, статус, `payload` JSON, необязательный `clientRequestId` для защиты от повторной отправки, необязательный срок `dueAt`, причина отклонения, необязательный исполнитель, даты создания и обновления.
- `RequestStatusHistory` — запись перехода: заявка, статус «из» (пустой для создания), статус «в», комментарий, автор изменения (если есть), дата. Записи не редактируются и не удаляются.

### Статусы и переходы

Статусы: `NEW`, `IN_PROGRESS`, `READY`, `REJECTED` из PRD и согласованный `CANCELLED` для отмены. Переходы:

- `NEW → IN_PROGRESS` — сотрудник деканата;
- `NEW → CANCELLED` — студент-владелец, только в `NEW`, с подтверждением в интерфейсе;
- `NEW → READY` и `NEW → REJECTED` — запрещены: заявка сначала берётся в работу;
- `IN_PROGRESS → READY` — сотрудник;
- `IN_PROGRESS → REJECTED` — сотрудник, причина обязательна;
- `READY`, `REJECTED` и `CANCELLED` — терминальные.

Отмена не удаляет заявку: она остаётся в списке и истории, чтобы студент видел путь заявки. Отмена в `IN_PROGRESS` и отмена невладельцем запрещены.

Допустимость перехода проверяется в серверной функции рядом с данными, а не только в интерфейсе. Смена статуса и запись истории выполняются в одной транзакции; уведомление создаётся в той же транзакции по контракту `P5-BE-02`, чтобы не оставить статус без события. Если создание уведомления не удалось, транзакция откатывается.

Базовая модель `Notification` добавляется в `P4-BE-01` вместе с заявками: без неё контракт `P5-BE-02` не на что опереть. `P5-BE-01` позже добавляет отметки прочтения и выборки аудитории, но не пересоздаёт модель и не меняет её поля.

### Поля типов

`payload` проверяется дискриминированной Zod-схемой по `typeCode`; схема — единый источник правил для формы и сервера. Состав полей согласован 17.11.2026:

- `STUDY_CERTIFICATE` — место предоставления;
- `PLACE_REQUIREMENT` — организация и место предоставления;
- `ACADEMIC_LEAVE` — причина, дата начала и окончания;
- `RETAKE` — дисциплина и причина.

Ограничения длины, правила дат и требования к `disciplineId` зафиксированы в спецификации § 4.3. Схема не принимает `studentId`, номер, статус и даты создания из клиента: они определяются на сервере.

### Номер и идемпотентность

Номер заявки генерируется на сервере в транзакции и уникален. Формат `З-{YYYY}-{6 цифр}` согласован 17.11.2026; год берётся по Москве. Счётчик хранится в `RequestNumberSequence` по году и увеличивается атомарно параметризованным SQL в той же транзакции: `INSERT … ON CONFLICT (year) DO UPDATE … RETURNING`. Сырой SQL оправдан гонкой на последовательности и не содержит конкатенации значений.

Для защиты от двойной отправки клиент передаёт `clientRequestId`; пара «студент + `clientRequestId`» уникальна. Повтор возвращает существующую заявку без создания второй; другой `typeCode` при том же `clientRequestId` — `CONFLICT`. Дополнительно действует лимит 10 заявок за 10 минут на студента (подсчёт по `createdAt` в БД), превышение — `RATE_LIMITED`.

### Индексы

- `request(number)` — уникальность номера;
- `request(studentId, createdAt)` — список студента;
- `request(studentId, clientRequestId)` — уникальность идемпотентности;
- `request(status, createdAt)` — очередь сотрудника;
- `request(typeId)` — связь со справочником;
- `requestStatusHistory(requestId, createdAt)` — история заявки;
- `requestType(code)` — уникальность кода;
- `requestNumberSequence(year)` — первичный ключ счётчика номеров.

`Notification` получает `dedupeKey` с уникальным индексом: повторная запись события статуса не создаёт дубль уведомления.

### Доступ

- Студент читает и отменяет только свои заявки; `studentId` берётся из проверенной сессии. Чужая заявка возвращает нейтральное «не найдено».
- Сотрудник видит очередь и меняет статусы только в рамках матрицы RBAC; персональные данные в очереди минимальны.
- Создание заявки доступно только студенту; сотрудник не создаёт заявку от его имени.
- Клиентский `userId`, `studentId`, номер и статус не принимаются как источник истины.

## Последствия

- `P4-BE-01` добавляет `RequestType`, `Request`, `RequestStatusHistory`, `RequestNumberSequence`, базовый `Notification`, перечисления и индексы, а также демонстрационный справочник типов, заявки, историю и уведомления.
- `P4-BE-02` добавляет Zod-схемы в `src/lib/validation/requests.ts`; форма и сервер используют одни и те же схемы.
- `P4-BE-03` реализует создание в транзакции: номер, дата, `NEW`, первая запись истории, уведомление, идемпотентность.
- `P4-BE-04` реализует выборки и переходы с проверкой владельца и роли; `P4-BE-05` покрывает создание, дубли, отмену, запрещённые переходы, чужую заявку и уведомление.
- `payload` не защищён ограничениями базы: любая запись проходит Zod-валидацию, а чтение не доверяет форме данных. Это осознанная цена за единый список и простой новый тип.
- Изменение статусов, формата номера, обязательных полей типа или лимита требует правки спецификации и, как правило, новой миграции; молчаливая смена контракта запрещена.
- Сотрудник деканата остаётся опциональным по PRD (`US-11`), но в проекте кабинет включён: очередь, карточка, смена статуса и комментарий реализованы без изменения модели данных.

### Дополнение: кабинет сотрудника (20.11.2026)

Кабинет использует существующие `Request`, `RequestStatusHistory` и `User.role`, миграция не требуется. Очередь строится доменной функцией `listRequestQueueForActor`: роль проверяется рядом с данными, без фильтра показываются `NEW` и `IN_PROGRESS`, новые идут раньше взятых в работу, внутри группы — старые сверху. Карточка `getRequest` возвращает сотруднику данные студента, исполнителя и допустимые переходы; студент те же поля не получает. Смена статуса и комментарий выполняются существующим `transitionRequestStatusForActor` в транзакции с историей и уведомлением. Демо-аккаунт сотрудника создаётся seed с ролью `DEAN_EMPLOYEE` и хешированным паролем Better Auth; заявки «в работе» назначаются ему. Студенческий интерфейс заявок остаётся отдельным объёмом `P4-FE-*`.
