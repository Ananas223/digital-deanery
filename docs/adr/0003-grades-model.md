# ADR 0003. Модель успеваемости

| Поле | Значение |
| --- | --- |
| Статус | Принято |
| Дата | 16.11.2026 |
| Контекст | Этап 3, задача `P3-BE-01`; требования `Ф-03`, `US-04`, `US-05` в `docs/PRD.md` |
| Связанные документы | `docs/PRD.md`, `docs/DEVELOPMENT_PLAN.md`, `AGENTS.md` § 2.4, § 3.2 |

## Контекст

Студенту нужна картина успеваемости: дисциплины семестра с формой контроля, зачётными единицами и итоговой оценкой, отдельный список экзаменов и зачётов сессии, сводка со средним баллом и задолженностями, а также история прошлых семестров. Данные читаются только для текущего студента, поэтому запросы обязаны опираться на `StudentProfile` из серверной сессии.

`Discipline` уже введена на этапе 2 и используется занятиями. По ADR 0002 `P3-BE-01` дополняет её связью с семестром и оценками и не создаёт вторую модель с тем же смыслом.

## Решение

### Сущности

- `Semester` — семестр: учебный год строкой (`2026/2027`), половина года (`AUTUMN`, `SPRING`), даты начала и окончания. Пара «учебный год + половина года» уникальна.
- `Grade` — итоговый результат студента по дисциплине в семестре: форма контроля, зачётные единицы, необязательный числовой балл и статус. Одна запись на студента, дисциплину и семестр.
- `Exam` — событие сессии для группы: дисциплина, семестр, форма контроля, начало и окончание, необязательные аудитория и преподаватель. Результат хранится в `Grade`.

`Grade.assessmentType` и `Grade.credits` повторяют учебный план для каждого студента. Отдельная сущность учебного плана (`CurriculumItem`) для прототипа не вводится: она усложняет схему и seed, не добавляя сценариев сверх `Ф-03`. Если появятся разные планы групп, `CurriculumItem` добавляется отдельной задачей и миграцией, а `Grade` получает ссылку на него.

### Формы контроля и оценки

`AssessmentType`:

- `EXAM` — экзамен;
- `CREDIT` — зачёт;
- `GRADED_CREDIT` — дифференцированный зачёт;
- `COURSEWORK` — курсовая работа.

`GradeStatus`:

- `PASSED` — зачёт получен или оценка положительная;
- `FAILED` — незачёт или неудовлетворительная оценка;
- `NOT_GRADED` — результат ещё не выставлен.

Правила согласованности:

- `score` — целое число от 2 до 5 или `null`; для `CREDIT` балл не используется;
- `score >= 3` соответствует `PASSED`, `score <= 2` — `FAILED`;
- для `CREDIT` статус выставляется отдельно, балл остаётся `null`;
- по умолчанию `status = NOT_GRADED`, `score = null`;
- диапазон балла проверяется Zod-схемой и доменным кодом на сервере; Prisma check-ограничения не используются.

Статус не вычисляется в базе: разные формы контроля требуют разных правил, а интерфейсу нужен и явный статус, и балл. Единый нормализатор появится в `P3-BE-03` вместе с расчётом сводки.

### Сессия

`Exam` привязан к группе, а не к студенту: расписание экзамена общее для группы. Студент видит экзамены своей группы по семестру; прошедший результат берётся из `Grade`. Аудитория и преподаватель необязательны: у зачёта может быть не назначена аудитория, а преподаватель может быть заменён.

### Индексы

- `semester(academicYear, term)` — уникальность семестра;
- `semester(startsAt)` — сортировка текущего и прошлых семестров;
- `grade(studentProfileId, semesterId)` — основной запрос «мои оценки за семестр»;
- `grade(studentProfileId, disciplineId, semesterId)` — уникальность результата;
- `grade(disciplineId)` — переход к дисциплине;
- `exam(groupId, startsAt)` — расписание сессии группы;
- `exam(semesterId, startsAt)` — сессия семестра;
- `exam(groupId, disciplineId, semesterId)` — уникальность экзамена;
- `exam(disciplineId)` — связь с дисциплиной.

### Доступ и seed

- `P3-BE-02` читает оценки по `studentProfileId` из проверенной сессии; клиентский идентификатор студента не принимается. Чужая дисциплина и чужой семестр возвращают пустой результат, а не данные другого студента.
- `P3-BE-04` заполняет два семестра: текущий и прошлый. У Анны и Марка заметно разные результаты, включая задолженность и незаполненную оценку. Seed идемпотентен: записи обновляются по естественным ключам, а не дублируются.
- Даты семестров и экзаменов хранятся в UTC; отображение — `Europe/Moscow`.

## Рассмотренные альтернативы

| Вариант | Почему отклонён |
| --- | --- |
| Отдельная модель учебного плана (`CurriculumItem`) | Больше сущностей и seed без новых сценариев `Ф-03`; добавляется позже при необходимости |
| Хранить оценку за каждое занятие | PRD требует итоговую оценку по дисциплине и семестру, а не журнал посещаемости |
| Хранить балл как enum `TWO`…`FIVE` | Усложняет расчёт среднего балла; `Int` с проверкой диапазона проще |
| Вычислять статус только из балла | Зачёт не имеет балла; для `CREDIT` нужен явный `PASSED`/`FAILED` |
| Дублировать `Discipline` для успеваемости | Нарушает ADR 0002 и создаёт две несвязанные модели одной сущности |
| Хранить название дисциплины и преподавателя в оценке | Дублирование и расхождение с расписанием |

## Последствия

- `P3-BE-02` реализует выборку дисциплин и оценок по студенту и семестру, включая прошлые семестры; сортировка — по названию дисциплины, семестры — от нового к старому. Тем же контрактом читается сессия семестра: экзамены группы с аудиторией, преподавателем и результатом из `Grade` (`US-05`).
- `P3-BE-03` считает средний балл только по числовым оценкам, суммирует полученные и запланированные зачётные единицы и определяет задолженности по `FAILED` и `NOT_GRADED` с истёкшим сроком.
- `P3-BE-04` добавляет текущий и прошлый семестры, экзамены сессии и результаты двух студентов; демо-данные вымышлены.
- `P3-BE-05` проверяет изоляцию студентов, корректность среднего балла, отсутствие оценок, зачёт/незачёт и пустой семестр.
- Форма контроля и зачётные единицы дублируются в `Grade`; при появлении нескольких учебных планов потребуется `CurriculumItem` и миграция.
