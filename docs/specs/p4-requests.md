# SPEC-P4-REQUESTS — заявки и справки

| Поле           | Значение                                                                                                |
| -------------- | ------------------------------------------------------------------------------------------------------- |
| ID             | `SPEC-P4-REQUESTS`                                                                                      |
| Название       | Заявки и справки: каталог, создание, статусы, история, отмена                                           |
| Статус         | Согласовано                                                                                             |
| Версия         | `1.0`                                                                                                   |
| Дата           | 17.11.2026                                                                                              |
| Требования PRD | `Ф-04.1`–`Ф-04.9`, `US-06`, `US-07`, `US-08`, `US-11` (опционально), `A-05`, `A-06`, `A-08`, `A-09`     |
| Задачи плана   | `P4-BE-01`–`P4-BE-05`, `P4-FE-01`–`P4-FE-05`, `P4-OPT-BE-01`, `P4-OPT-FE-01`, `P4-GATE-01`–`P4-GATE-03` |
| Связанные ADR  | [`docs/adr/0004-requests-model.md`](../adr/0004-requests-model.md) (Принято)                            |
| Заменяет       | —                                                                                                       |

## 1. Проблема и цель

Студенту нужна справка или заявление без похода в деканат: выбрать тип, заполнить только нужные поля, получить номер и видеть путь заявки до результата. Backend заявок реализован (`P4-BE-01`–`P4-BE-05`), включая модели Prisma, серверные действия и интеграционные тесты. Интерфейс ещё не подключён: раздел показывает пустое состояние, а E2E-сценарии заявок и общие гейты приёмки остаются незавершёнными.

**Готово, если:** студент создаёт заявку, видит номер и статус «Новая», после перезагрузки и повторного входа находит её в списке, а смена статуса отражается в истории и порождает уведомление.

## 2. Границы

**Входит:**

- каталог из четырёх типов: справка об обучении, справка по месту требования, академический отпуск, пересдача;
- форма, зависящая от типа, с серверной валидацией;
- создание заявки в транзакции: номер, дата, статус «Новая», запись истории, уведомление;
- список «Мои заявки» с фильтром по статусу и пустым состоянием;
- карточка с данными, историей статусов, причиной отклонения, отменой в статусе «Новая»;
- серверные переходы статусов с проверкой роли; интерфейс сотрудника — опционально (`US-11`).

**Не входит:**

- вложения и загрузка файлов (PRD § 11);
- скачивание готовой справки в PDF;
- e-mail, push и мессенджеры;
- статистика и расширенный кабинет сотрудника (PRD § 6, P2);
- юридически значимый документооборот.

**Явные допущения:**

> **Допущение:** для демонстрации смена статуса может выполняться сидированными данными и серверным действием сотрудника; полноценный интерфейс сотрудника остаётся опциональным. **Почему:** `P4-GATE-03` допускает «неприменимо» для `US-11`. **Влияние:** `A-06` проверяется интеграционно и на сидированных статусах, а не только через UI сотрудника. **Как проверить:** интеграционный тест перехода и уведомления; E2E `US-07` на подготовленных данных.

| Сценарий       | Роль      | Предусловия                              | Шаги                                                                 | Результат                                                        | Исключения                                                           |

| `US-06`        | студент   | вход выполнен                            | «Заказать справку» → тип → форма → отправка → подтверждение          | номер, дата, статус «Новая»; заявка в списке и на главном экране | обязательное поле не заполнено; двойная отправка; сервер недоступен  |
| `US-07`        | студент   | заявка создана                           | уведомление → карточка → история → следующее уведомление             | актуальный статус и следующий шаг                                | статус изменился, пока страница открыта; заявка отменена             |

### 4.2. Enum-типы и статусы

| Тип             | Значения                                               | Переходы / правила                                    |
| --------------- | ------------------------------------------------------ | ----------------------------------------------------- |
| `RequestStatus` | `NEW`, `IN_PROGRESS`, `READY`, `REJECTED`, `CANCELLED` | `CANCELLED` согласован владельцем продукта 17.11.2026 |

Допустимые переходы:

| Из                                 | В             | Кто                | Условия                                              |
| ---------------------------------- | ------------- | ------------------ | ---------------------------------------------------- |
| `NEW`                              | `IN_PROGRESS` | `DEAN_EMPLOYEE`    | заявка существует; роль проверена на сервере         |
| `NEW`                              | `CANCELLED`   | `STUDENT`-владелец | подтверждение в UI; отмена в `IN_PROGRESS` запрещена |
| `IN_PROGRESS`                      | `READY`       | `DEAN_EMPLOYEE`    | —                                                    |
| `IN_PROGRESS`                      | `REJECTED`    | `DEAN_EMPLOYEE`    | `rejectionReason` обязательна, непустая              |
| `READY` / `REJECTED` / `CANCELLED` | —             | —                  | терминальные; изменения запрещены                    |

Запрещены: `NEW → READY`, `NEW → REJECTED`, `IN_PROGRESS → NEW`, любой переход из терминального статуса, отмена невладельцем, отмена в `IN_PROGRESS`. Отклонение сразу из `NEW` запрещено: заявка сначала берётся в работу. Каждый переход пишется в `RequestStatusHistory` в той же транзакции.

### 4.3. Zod-схемы

| Схема                           | Файл (план)                      | Поля                                                                               | Используется        |
| ------------------------------- | -------------------------------- | ---------------------------------------------------------------------------------- | ------------------- |
| `requestTypeCodeSchema`         | `src/lib/validation/requests.ts` | enum из четырёх кодов                                                              | форма и сервер      |
| `requestPayloadSchema`          | там же                           | discriminated union по `typeCode`; член `{ typeCode, payload }`                    | форма и сервер      |
| `createRequestSchema`           | там же                           | discriminated union по `typeCode`: `{ typeCode, clientRequestId (uuid), payload }` | форма и сервер      |
| `requestListQuerySchema`        | там же                           | `status?` из `RequestStatus`                                                       | список              |
| `cancelRequestSchema`           | там же                           | `requestId`                                                                        | отмена              |
| `requestStatusTransitionSchema` | там же                           | `requestId`, `toStatus`, `comment?`                                                | действие сотрудника |

Минимальный состав полей payload (согласован 17.11.2026):

| Тип                 | Поля                                            |
| ------------------- | ----------------------------------------------- |
| `STUDY_CERTIFICATE` | `deliveryPlace` (куда), `comment?`              |
| `PLACE_REQUIREMENT` | `organizationName`, `deliveryPlace`, `comment?` |
| `ACADEMIC_LEAVE`    | `reason`, `startDate`, `endDate`, `comment?`    |
| `RETAKE`            | `disciplineId`, `reason`, `comment?`            |

Правила полей (согласованы 17.11.2026):

- `deliveryPlace` — строка 5–200 символов; `organizationName` — 2–200; `reason` — 10–500; `comment?` — до 500 символов. Строки обрезаются по краям, пустые не принимаются.
- `startDate` и `endDate` — даты `YYYY-MM-DD`; `startDate` не позже `endDate`.
- `disciplineId` — `cuid()` существующей дисциплины; проверка существования — на сервере.
- `payload` не дублирует `typeCode`: тип лежит на верхнем уровне заявки; в БД сохраняется только `payload` соответствующего типа.
- `requestPayloadSchema` описывает пару «тип + payload» для формы, `createRequestSchema` добавляет `clientRequestId`. Обе схемы экспортируются из одного файла и используются формой и Server Action.

Сервер не доверяет клиентской валидации: те же схемы применяются в Server Action. `payload` в БД хранится только после успешного разбора схемой.

### 4.4. Server Actions и Route Handlers

| Действие                  | Сигнатура (план)                                                       | Права                            | Ошибки                                                                |
| ------------------------- | ---------------------------------------------------------------------- | -------------------------------- | --------------------------------------------------------------------- |
| `createRequest`           | `(input: CreateRequestInput) => Promise<ActionResult<RequestCreated>>` | `STUDENT`                        | `VALIDATION_ERROR`, `RATE_LIMITED`, `CONFLICT`, `FORBIDDEN`           |
| `cancelRequest`           | `(requestId: string) => Promise<ActionResult<void>>`                   | `STUDENT`-владелец               | `NOT_FOUND` (в т. ч. чужая), `FORBIDDEN` (роль), `INVALID_TRANSITION` |
| `getMyRequests`           | `(filter?: RequestListQuery) => Promise<RequestSummary[]>`             | `STUDENT`                        | —                                                                     |
| `getRequest`              | `(requestId: string) => Promise<RequestDetail \| null>`                | владелец; сотрудник — по матрице | `NOT_FOUND`                                                           |
| `transitionRequestStatus` | `(input: RequestStatusTransitionInput) => Promise<ActionResult<void>>` | `DEAN_EMPLOYEE`                  | `NOT_FOUND`, `FORBIDDEN`, `INVALID_TRANSITION`, `VALIDATION_ERROR`    |
| `listRequestQueue` (опц.) | `(filter?: RequestQueueQuery) => Promise<RequestQueueItem[]>`          | `DEAN_EMPLOYEE`                  | `FORBIDDEN`                                                           |

`ActionResult<T> = { ok: true; data: T } | { ok: false; error: { code: string; message: string; requestId: string } }`.

`userId`, `studentId` и роль берутся только из проверенной сессии. Клиентский `studentId` игнорируется.

Создание и смена статуса выполняются в `prisma.$transaction`: запись заявки/статуса, запись истории и уведомление (`P5-BE-02`) либо откатываются вместе. Уведомление создаётся в той же транзакции; его сбой откатывает заявку — заявка без события не остаётся.

Повтор с тем же `clientRequestId` не создаёт вторую заявку: действие возвращает существующую заявку с `ok: true` (идемпотентный повтор). Если с тем же `clientRequestId` пришёл другой `typeCode`, возвращается `CONFLICT`.

Лимит создания: не более 10 заявок одного студента за 10 минут (скользящее окно по `createdAt`, считается в БД до вставки). Превышение — `RATE_LIMITED`; лимит проверяется на сервере и не заменяет уникальный индекс.

### 4.5. Коды ошибок

| Код                     | Когда                                                                    | Сообщение пользователю           |
| ----------------------- | ------------------------------------------------------------------------ | -------------------------------- |
| `VALIDATION_ERROR`      | схема не прошла                                                          | «Проверьте заполнение полей»     |
| `NOT_FOUND`             | заявки нет или она чужая                                                 | «Заявка не найдена»              |
| `FORBIDDEN`             | роль не разрешает действие                                               | «Недостаточно прав»              |
| `INVALID_TRANSITION`    | переход запрещён                                                         | «Это действие сейчас недоступно» |
| ~~`DUPLICATE_REQUEST`~~ | не используется: тот же `clientRequestId` возвращает существующую заявку | —                                |
| `RATE_LIMITED`          | превышен лимит создания                                                  | «Попробуйте позже»               |
| `CONFLICT`              | статус изменился параллельно                                             | «Обновите страницу и повторите»  |

Коды `ActionResult.error.code` — публичные и совпадают с таблицей. Внутри доменного слоя используются коды `src/lib/errors.ts`: `VALIDATION_ERROR → VALIDATION`, `INVALID_TRANSITION → INVALID_TRANSITION`, `RATE_LIMITED → RATE_LIMITED`, остальные совпадают. `ErrorCode` расширяется значениями `INVALID_TRANSITION` (409) и `RATE_LIMITED` (429) с нейтральными сообщениями. Внутренние детали и стек пользователю не показываются.

## 5. Права и владение

| Роль            | Действие               | Ресурс                    | Проверка на сервере                                           |
| --------------- | ---------------------- | ------------------------- | ------------------------------------------------------------- |
| `STUDENT`       | создать                | своя заявка               | `studentId` из сессии; `clientRequestId` уникален             |
| `STUDENT`       | читать список/карточку | только свои               | `where.studentId = session.studentId`; чужой id → `NOT_FOUND` |
| `STUDENT`       | отменить               | только своя, только `NEW` | владелец + статус + допустимый переход                        |
| `DEAN_EMPLOYEE` | очередь и карточка     | заявки студентов          | роль из сессии; минимум полей                                 |
| `DEAN_EMPLOYEE` | сменить статус         | заявка в очереди          | роль + допустимый переход + причина при отказе                |
| `DEAN_EMPLOYEE` | комментарий            | заявка                    | роль; комментарий виден студенту                              |

Запрещено по умолчанию. Скрытие кнопки в UI не заменяет серверную проверку. Студент не выполняет действия сотрудника; сотрудник не получает доступ к чужим оценкам, расписанию и профилю сверх необходимого.

### 6.2. Состояния

| Состояние        | Где                       | Что видит студент                    | Что можно сделать                 |
| ---------------- | ------------------------- | ------------------------------------ | --------------------------------- |
| Загрузка         | каталог, список, карточка | скелетон, не пустой экран            | —                                 |
| Пусто            | список                    | «Заявок пока нет» + «Создать первую» | перейти в каталог                 |
| Ошибка           | форма, список, карточка   | нейтральное сообщение и «Повторить»  | повторить; данные формы сохранены |
| Успех            | после создания            | номер, дата, статус «Новая»          | открыть заявку или вернуться      |
| Частичная ошибка | главный экран             | блок заявок не ломает остальные      | обновить блок                     |

### 6.3. Мобильный опыт и доступность

- 360 px: каталог и форма — одна колонка; карточка — вертикальная временная шкала; нет горизонтальной прокрутки.
- 390/768/1280 px: каталог сеткой, карточка с боковой историей; формы не шире читаемой колонки.
- Клавиатура: фокус в форме, диалог отмены с ловушкой фокуса и закрытием по Escape; подписи полей обязательны.
- Статусы дублируются текстом, не только цветом.
- `prefers-reduced-motion`: анимации переходов отключаются.

## 7. Критерии приёмки

- [ ] `A-05`: заявка получает номер, статус «Новая» и сохраняется после повторного входа.
- [ ] `A-06`: смена статуса обновляет историю, создаёт уведомление и не теряет данные.
- [ ] `US-06`: создание справки об обучении с подтверждением и появлением в списке.
- [ ] `US-07`: переход по уведомлению в карточку, история и следующий шаг.
- [ ] `US-08`: отклонение с обязательной причиной и повторное создание без дубля.
- [ ] `US-11` (если включён): сотрудник переводит заявку и оставляет комментарий; иначе `P4-GATE-03` помечен «неприменимо».
- [ ] Чужая заявка недоступна по прямому адресу; ответ нейтрален.
- [ ] Отмена доступна только в `NEW` и требует подтверждения.
- [ ] На 360 px каталог, форма и карточка проходятся без горизонтальной прокрутки.
- [ ] Загрузка, пусто, ошибка, успех и частичная ошибка предусмотрены.

## 9. Зависимости и риски

- Зависит от `P1-BE-01` (профиль и студент из сессии), `P0-BE-04` (сессия), `P0-BE-06` (ошибки и владение).
- Зависит от контракта уведомлений `P5-BE-02`. Базовая модель `Notification` добавляется уже в `P4-BE-01` как общий контракт; `P5-BE-01` позже добавляет отметки прочтения и выборки аудитории, а не саму модель.
- Создание заявки не должно оставлять статус без события: уведомление пишется в той же транзакции, сбой откатывает создание.
- Ограничение частоты создания опирается на `createdAt` заявок и не требует внешнего хранилища; демо-заявки сидируются с датой вне окна лимита.
- Статусная заявка уже записывает уведомление о смене статуса в той же транзакции (§ 4.4); `P5` остаётся незавершённым для функций центра уведомлений — выбора аудитории, отметки прочтения и ленты. Блок активных заявок `P6` сохраняется.
- Риски: расползание полей по типам; конфликт статусов при параллельной смене; дубли при двойной отправке; отсутствие сотрудника для демонстрации `A-06`.
- Если `US-11` не включается, статусы для демонстрации готовятся seed-скриптом, а переходы проверяются интеграционно.

## 10. Принятые решения

Открытые вопросы черновика закрыты владельцем продукта 17.11.2026; молчаливая смена этих решений запрещена.

| Вопрос                         | Решение                                                               | Следствие                                                          |
| ------------------------------ | --------------------------------------------------------------------- | ------------------------------------------------------------------ |
| Статус отмены                  | `CANCELLED` — пятый статус, история сохраняется                       | `RequestStatus` из пяти значений; переход `NEW → CANCELLED`        |
| Формат номера                  | `З-{ГГГГ}-{6 цифр}`, год по Москве                                    | Таблица `RequestNumberSequence`, атомарная выдача в транзакции     |
| Поля по типам                  | Минимум из § 4.3                                                      | Zod-схемы по типам, форма и сервер используют одни правила         |
| Отклонение из `NEW`            | Запрещено; сначала `NEW → IN_PROGRESS`                                | Проверка перехода на сервере, отдельный тест                       |
| Сотрудник в демо               | Роль `DEAN_EMPLOYEE` + серверные переходы; интерфейс опционален       | `US-11` может быть «неприменимо», `A-06` проверяется интеграционно |
