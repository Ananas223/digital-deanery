## 0. Назначение и источники истины

Этот документ отвечает на вопрос **«как агент должен работать»**. Что именно делает продукт и как им пользуется студент, описано в `docs/PRD.md`.

| Документ | Отвечает за | Не содержит |
| --- | --- | --- |
| `docs/PRD.md` | Продуктовое поведение, функции `Ф-XX`, сценарии `US-XX`, критерии `A-XX` | Детали стека, процесс, детали безопасности |
| `docs/DEVELOPMENT_PLAN.md` | Пошаговый план ядра, статусы задач и прогресс | Продуктовые требования и инженерные правила |
| `AGENTS.md` (этот файл) | Инженерные ограничения, безопасность, качество, процесс, чек-листы | Пересказ функций и сценариев PRD |
| `docs/adr/` | Архитектурные решения и их обоснование | Продуктовые требования |
| `docs/ai-log.md` | Журнал инструментов, промптов и этапов работы | Технические инструкции |
| `README.md` | Запуск, окружение, демо-аккаунты | Правила разработки |

Файлы `docs/adr/`, `docs/ai-log.md`, `docs/third-party.md` и `README.md` создаются по мере работы над проектом. До их появления действуют правила этого документа; ссылка на ещё не созданный файл не отменяет требование.

**Приоритет документов при конфликте:**

1. Продуктовое поведение — `docs/PRD.md`.
2. Инженерные ограничения и безопасность — этот файл.
3. Архитектурные детали — принятый ADR.
4. Если ответа нет нигде — остановиться и задать вопрос человеку, не придумывать требование.

**Запрет на дублирование.** Не копировать в `AGENTS.md` описания функций, экранов и пользовательских сценариев. Вместо этого ссылаться на ID: `Ф-02`, `US-06`, `A-05`. Если правило относится к поведению продукта, оно должно жить в PRD, а здесь — только ссылка и способ проверки.

## 1. Обязательный протокол старта задачи

Перед любым изменением файлов:

1. Прочитать этот файл целиком, релевантные разделы `docs/PRD.md`, `docs/DEVELOPMENT_PLAN.md`, принятые ADR и `README.md`.
2. Проверить состояние репозитория (`git status`, текущая ветка). Не перезаписывать незакоммиченные изменения человека.
3. Сформулировать план: цель, затронутые файлы, способ проверки, риски. План должен быть коротким (3–7 пунктов).
4. Явно перечислить допущения. Если допущение влияет на продукт или безопасность — сначала спросить.
5. Реализовать минимальный законченный вертикальный срез, а не набор несвязанных заготовок.
6. Запустить проверки из § 6 и убедиться, что они проходят.
7. Обновить план и отчитаться: что изменено, какие проверки выполнены, что осталось, какие риски.

**Запрещено:** начинать код без чтения PRD; менять несвязанные файлы «заодно»; выдавать задачу за готовую без запуска проверок; молча менять продуктовое поведение.

### 1.1. Синхронизация плана разработки

- `docs/DEVELOPMENT_PLAN.md` — единственный источник статуса задач и прогресса. Не вести параллельный список задач в других файлах.
- Перед началом работы найти задачу по ID, проверить её зависимости и контракт. Задачи из независимых потоков можно вести одновременно; ждать закрытия всех предыдущих этапов не нужно.
- Бэкенд фиксирует контракт (`Zod`-схемы, сигнатуры Server Actions и Route Handlers, события уведомлений) до начала фронтенд-задачи. После фиксации контракта фронтенд и бэкенд идут параллельно.
- Один агент — один поток или одна задача. Два агента не правят одни и те же файлы одновременно; пересечения выносятся в отдельную задачу или согласуются до начала работы.
- После выполнения отметить пункт `[x]` только при пройденных проверках § 6. Частичную работу не отмечать.
- Обновить в плане «Обновлено», «Текущий фокус» и историю изменений. При необходимости добавить коммит рядом с задачей.
- Не удалять и не переписывать задачи. Новую работу добавлять с новым ID и ссылкой на исходную; блокер фиксировать строкой `> Блокер: ...`.
- Если задача отсутствует в плане, сначала добавить её, затем выполнять. Продуктовые детали не дублировать: ссылаться на `Ф-XX`, `US-XX`, `A-XX`.

## 2. Технологические рамки

### 2.1. Платформа и стек

- Продукт — **веб-приложение** на Next.js, открывающееся в современном браузере; установка не требуется.
- Стек зафиксирован для проекта:

| Слой | Технологии | Назначение |
| --- | --- | --- |
| Основа | Next.js (App Router), React, TypeScript (strict) | Интерфейс, серверные компоненты и маршрутизация в одном проекте |
| Сервер | Next.js Server Actions, Route Handlers, Zod | Изменения данных, API и серверная валидация |
| Интерфейс | Tailwind CSS v4, shadcn/ui, Base UI, Motion, Lucide React | Адаптивная вёрстка, доступные примитивы, анимации и иконки |
| Графики | Recharts | Визуализация успеваемости и сводок |
| Состояние UI | React Context + useReducer | Локальное состояние фильтров, диалогов и панелей |
| Формы | React Hook Form, Zod | Состояние форм, ошибки и единые схемы проверки |
| Данные | PostgreSQL, Prisma ORM | Студенты, группы, занятия, оценки, заявки, уведомления |
| Доступ | Better Auth, RBAC | Вход, серверные сессии, роли и матрица разрешений |
| AI | Vercel AI SDK, Agent Tools, LLM Provider API | ИИ-помощник по кабинету (опциональный трек) |
| Тесты | Playwright, Vitest | Браузерные сценарии и модульные проверки |

- **Версии:** TypeScript в strict-режиме; Tailwind CSS v4 с CSS-first токенами; Prisma ORM 7.x, пока Better Auth не подтвердит следующую мажорную версию. Версии фиксируются lock-файлом; мажорное обновление — только через ADR и полный прогон тестов.
- **UI-слой:** Base UI — примитивы доступности, shadcn/ui — паттерны и стили компонентов. Не смешивать два набора примитивов в одном компоненте. Tailwind CSS — единственная система стилей; случайные значения в разметке запрещены.
- **Motion:** анимации только для осмысленных переходов и обратной связи; обязателен `prefers-reduced-motion`.
- **Recharts:** только для графиков успеваемости и сводок; график — клиентский компонент с текстовой альтернативой данных.
- **React Context + useReducer:** только локальное UI-состояние. Серверные данные читаются через Server Components и Server Actions и не дублируются в Context; отдельный глобальный state-менеджер не добавляется.
- **RBAC:** роли `STUDENT` и `DEAN_EMPLOYEE`; матрица разрешений проверяется на сервере рядом с данными, а не в интерфейсе.
- **AI:** Vercel AI SDK, Agent Tools и LLM Provider API. Ключ провайдера хранится только на сервере; инструменты работают через сессию и read-only контракты, изменения данных — только после явного подтверждения студентом.
- Выбирать поддерживаемые версии без preview-функций; экзотические фреймворки и «второй стек» не добавлять.
- Требования к масштабированию: stateless-приложение Next.js, данные в PostgreSQL, конфигурация через переменные окружения, отсутствие привязки к локальному диску.
- Вопросы размещения и инфраструктуры в этом документе не рассматриваются.

### 2.2. Обязательные архитектурные правила

- Архитектура — **модульный монолит**: одно приложение Next.js, внутри — доменные модули (профиль, расписание, успеваемость, заявки, уведомления). Микросервисы и отдельный backend не добавлять.
- **Серверный слой обязателен.** Браузер не является источником истины для оценок, заявок и уведомлений.
- Данные сохраняются между перезагрузкой, повторным входом и сменой устройства.
- Слой доступа к данным отделён от UI. Компоненты не содержат Prisma-запросов и не решают, имеет ли пользователь право на ресурс. Доступ к Prisma — только из server-only модулей.
- Изменения данных выполняются через Server Actions или Route Handlers. Входные данные валидируются Zod-схемой на сервере; одна и та же схема используется формой и сервером.
- **Server Components — по умолчанию.** `use client` добавляется только для интерактивности, которой нельзя достичь на сервере.
- Один репозиторий и один документированный способ локального запуска. Локальная среда поднимается командой из `README.md`.
- Секреты и настройки — только через окружение; в репозитории хранится `.env.example` без значений.

### 2.3. Структура репозитория

Рекомендуемая структура (может уточняться в ADR, но не хаотично):

```text
digital-deanery/
  docs/                 # PRD, ADR, ai-log, сторонние материалы
  prisma/
    schema.prisma       # схема данных
    migrations/         # миграции Prisma
    seed.ts             # вымышленные демо-данные
  src/
    app/                # App Router: страницы, layouts, Route Handlers
    components/
      ui/               # компоненты shadcn/ui
      ...               # доменные компоненты
    lib/
      auth/             # конфигурация и серверные помощники Better Auth
      db/               # Prisma Client
      validation/       # Zod-схемы
      domain/           # бизнес-логика и проверки доступа
  public/               # статические ресурсы
  tests/
    unit/               # Vitest
    e2e/                # Playwright
  scripts/              # вспомогательные скрипты
  README.md
  AGENTS.md
```

- Файлы размещать рядом с их зоной ответственности; не создавать «свалку» из утилит.
- Один файл не должен разрастаться до неуправляемого размера: выделять модули по смыслу.
- Не оставлять параллельные реализации одной функции «на всякий случай».

### 2.4. База данных

- Схема находится в `prisma/schema.prisma` и изменяется только миграциями Prisma; ручные правки схемы запрещены.
- Миграции применяются одной командой; структура воспроизводима на чистой базе.
- Seed-скрипт `prisma/seed.ts` создаёт демонстрационные данные и может запускаться повторно без дублей.
- Prisma Client создаётся один раз в `src/lib/db` и переиспользуется, чтобы не плодить соединения при горячей перезагрузке.
- Переходы статусов заявок выполняются в `prisma.$transaction` с проверкой допустимости перехода.
- Для часто используемых выборок (пользователь, заявки, уведомления) предусмотрены индексы в схеме Prisma.
- Даты и время хранятся в UTC, отображаются в московском часовом поясе.

### 2.5. Клиентская часть

- Состояние сервера читается через Server Components и Server Actions; оно не подменяется локальным хранилищем. `localStorage` допустим только для нечувствительных UI-настроек (например, тема), но не для сессии, оценок и заявок.
- Локальное состояние интерфейса — React Context + `useReducer`. Контекст не заменяет серверные данные и не становится вторым источником истины.
- Формы строятся на React Hook Form с `zodResolver`; сервер повторно проверяет те же Zod-схемы и не доверяет клиентской валидации.
- Стилизация — Tailwind CSS v4 и компоненты shadcn/ui на примитивах Base UI. shadcn/ui — база, а не готовый дизайн: компоненты приводятся к собственному визуальному стилю.
- Анимации — Motion, только для осмысленных переходов и обратной связи; при `prefers-reduced-motion` движение отключается.
- Графики — Recharts, только для задач визуализации; каждый график сопровождается текстовой сводкой, доступной без наведения.
- Иконки — Lucide React, один набор на весь интерфейс.
- Сессия и вход на клиенте — через Better Auth; самописные cookie, токены в `localStorage` и собственная сессионная логика запрещены.
- Секреты, ключи и пароли никогда не попадают в клиентский бандл.
- Зависимости добавляются только при реальной необходимости, с проверкой лицензии и поддержки.

## 3. Безопасность (обязательно, не обсуждается)

Требования продукта к приватности описаны в PRD (`Ф-01`, § 8.7); здесь — как это обеспечить технически.

### 3.1. Пароли и сессии

- Аутентификация и сессии — **Better Auth**. Пароли хешируются Better Auth (scrypt по умолчанию); открытый текст, обратимое шифрование и понижение параметров хеширования запрещены.
- Демонстрационные пароли создаются seed-скриптом через Better Auth и хранятся хешированными; в документации для жюри они указаны отдельно.
- Сессионные cookie Better Auth настраиваются с флагами `HttpOnly`, `Secure`, `SameSite=Lax` (или строже). Собственная реализация сессий запрещена.
- Вход и выход выполняются через Better Auth; сессия проверяется на сервере при каждом защищённом запросе.
- Неудачный вход не раскрывает, существует ли логин. Сообщения нейтральны.
- Действует ограничение частоты попыток входа и создания заявок; для auth-маршрутов используется встроенный или серверный rate limit.

### 3.2. Авторизация и RBAC

- Better Auth подтверждает личность, но не заменяет авторизацию. После получения сессии приложение отдельно проверяет владельца ресурса и роль пользователя.
- **RBAC:** роль хранится на сервере (`STUDENT`, `DEAN_EMPLOYEE`). Матрица «роль → действие → ресурс» описана в одном серверном модуле и применяется в Server Actions и Route Handlers. Клиентская проверка роли — только подсказка интерфейсу.
- Студент действует только со своими профилем, оценками, заявками и уведомлениями. Сотрудник деканата получает только те действия, которые явно разрешены матрицей; доступ к чужим персональным данным без необходимости запрещён.
- Каждый запрос к защищённому ресурсу определяет пользователя на сервере. Нельзя доверять `userId`, переданному клиентом.
- Проверка владения ресурсом обязательна для чтения **и** записи: профиль, заявка, уведомление, расписание, оценка.
- Принцип «запрещено по умолчанию»: нет явного разрешения — нет доступа.
- Чужой ресурс возвращает нейтральный ответ «не найдено» или «нет доступа», не раскрывая существование объекта.
- Скрытие кнопки в интерфейсе не является защитой. Проверка на сервере обязательна даже если UI её дублирует.
- Next.js middleware допускается для редиректов и грубой фильтрации, но не как единственная проверка прав. Решение о доступе принимается в серверном слое рядом с данными.
- Для каждого сценария доступа пишутся автоматические тесты: пользователь A не читает и не изменяет ресурсы пользователя B; студент не выполняет действия сотрудника.

### 3.3. Валидация и обработка данных

- Zod — единый источник правил валидации для React Hook Form и сервера. Сервер проверяет входные данные повторно, независимо от клиента.
- Запросы к БД выполняются через Prisma. Сырой SQL допустим только через параметризованный `$queryRaw` с обоснованием; конкатенация SQL запрещена.
- Вывод экранируется; `dangerouslySetInnerHTML` и аналоги — только для доверенного санитизированного контента.
- Для state-changing запросов используется CSRF-защита: встроенные проверки Server Actions и Better Auth, при необходимости — дополнительная проверка Origin и SameSite.
- Загрузка файлов, если появится: ограничение типа и размера, случайные имена, хранение вне публичной директории, запрет исполнения.
- Ошибки пользователю — короткие и нейтральные; стек, SQL и внутренние детали показываются только в серверных логах.

### 3.4. Секреты и ключи

- Ключи, пароли и токены — только в переменных окружения на сервере. `.env` в `.gitignore`.
- `DATABASE_URL`, `BETTER_AUTH_SECRET` и другие серверные значения не получают префикс `NEXT_PUBLIC_` и не попадают в клиентский бандл.
- Перед сдачей проверить клиентский бандл на наличие ключей и паролей.
- Не выводить секреты в логи, скриншоты, сообщения об ошибках и демонстрационные данные.
- При подозрении на утечку — немедленно сообщить человеку и ротировать значение.

### 3.5. Заголовки, кеш и логи

- Базовые security-заголовки: `Content-Security-Policy`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, защита от кликджекинга.
- Персональные страницы и ответы не попадают в общий кеш Next.js: для них используется динамический рендер и `cache: 'no-store'`; `unstable_cache` для персонализированных данных запрещён.
- Административные и служебные действия сотрудника требуют авторизации и проверки роли на сервере.
- Логи не содержат паролей, токенов, cookie, тел auth-запросов и персональных данных.

### 3.6. Зависимости и совместимость

- Перед добавлением пакета проверить лицензию, поддержку и репутацию.
- Фиксировать версии lock-файлом; обновления — осознанно.
- Соблюдать совместимость Prisma ORM, Better Auth, Base UI и Vercel AI SDK (§ 2.1). Мажорные обновления Prisma, Better Auth, Next.js, React, Base UI и AI SDK — только через ADR и полный прогон тестов.
- Запрещены пакеты с неясной лицензией, заброшенные или дублирующие уже имеющуюся функциональность.
- Сторонние скрипты с CDN — только при необходимости и с проверкой целостности.

### 3.7. ИИ-помощник (опциональный трек)

- Стек — **Vercel AI SDK + Agent Tools + LLM Provider API**. Вызов модели выполняется только на сервере; ключ провайдера хранится в переменных окружения и не попадает в браузер.
- Agent Tools описываются на сервере с Zod-схемами входа. Инструмент получает `userId` из проверенной сессии, а не из аргументов, сгенерированных моделью.
- Инструменты по умолчанию только читают данные. Создание заявки, отмена или иное изменение выполняются обычным Server Action после явного подтверждения студентом и серверной проверки прав.
- В модель передаётся минимум необходимых данных. Запрещено отправлять пароли, cookie, токены, номера студенческих и другие персональные данные, без которых можно обойтись.
- Список инструментов фиксирован; произвольный SQL, доступ к файлам и выполнение кода из ответа модели запрещены. Ответ модели выводится как текст, без `dangerouslySetInnerHTML`.
- Действуют ограничения частоты запросов и бюджета токенов. Ошибка или недоступность провайдера не блокирует ядровые разделы: помощник показывает нейтральное сообщение и предлагает повторить.
- Логи содержат идентификатор запроса, имя инструмента и длительность, но не полные промпты с персональными данными.

## 4. Данные, контент и правовые ограничения

### 4.1. Только вымышленные данные

- Все ФИО, оценки, номера студенческих, телефоны, e-mail, адреса и преподаватели — вымышлены.
- Запрещено использовать данные реальных студентов, сотрудников и преподавателей, даже найденные в открытых источниках.
- Запрещено подключаться к реальным информационным системам вуза и использовать настоящие учётные данные.
- Парсинг открытых данных (например, расписания) допустим, но только как снимок публичной информации, без обхода авторизации и без выдачи результата за официальные данные вуза. Источник фиксируется в документации.

### 4.2. Демонстрационные аккаунты

- Минимум два аккаунта студентов с заметно разными профилями, расписанием, оценками, заявками и уведомлениями.
- При наличии кабинета сотрудника — отдельный аккаунт с ограниченной ролью.
- Данные аккаунтов создаются seed-скриптом; пароли хранятся хешированными.
- Учётные данные для жюри описаны в `README.md` и не дублируются в коде.
- Должна существовать команда сброса демо-данных к исходному состоянию.

### 4.3. Оформление и правовые требования

- На всех страницах или в постоянном футере видно, что это учебный концепт для конкурса, а не официальный сервис вуза.
- Официальный логотип вуза не используется. Собственный логотип не копирует оригинальный.
- Название и реалии вуза допустимы, но не создают впечатления официального сервиса.
- Используются только лицензионно совместимые шрифты, иконки, изображения и библиотеки.
- Каждый сторонний материал фиксируется в `docs/third-party.md`: название, автор/источник, лицензия, ссылка. Запрещены материалы без лицензии и «найденные в интернете».
- Изображения, сгенерированные ИИ, допустимы, если не воспроизводят чужой товарный знак или защищённый персонаж; факт генерации фиксируется.

### 4.4. Качество контента

- Форматирование дат, времени и чисел централизовано (локаль `ru-RU`, часовой пояс `Europe/Moscow`); ручные строки в компонентах запрещены.
- Никакого «рыбного» текста, заглушек и неработающих ссылок в ядровых экранах (требование к содержанию — PRD § 8.6).
- Тексты короткие, конкретные, без внутренних кодов и канцелярита.
- Демонстрационные данные реалистичны: названия дисциплин, типы занятий, аудитории, формы контроля.

## 5. Интерфейс: инженерные требования

Сквозные требования к опыту — навигация, мобильный опыт, состояния, доступность, контент, приватность и воспринимаемая производительность — заданы в `docs/PRD.md` § 8. Ниже описаны инженерные способы их реализации и проверки; пересказывать PRD не нужно.

### 5.1. Адаптивная реализация

- Mobile-first CSS и единые breakpoints; отдельная мобильная сборка или поддомен запрещены.
- Проверка на 360, 390, 768 и 1280 px; для 360 px обязателен E2E-прогон сценариев `US-01`–`US-09`.
- Плотные таблицы реализуются одним компонентом, который на узком экране превращается в карточки или список.
- Навигация: нижняя панель на мобильном, боковое меню на широком экране; не показывать оба меню одновременно.
- Формы и диалоги не вызывают горизонтальную прокрутку и не перекрываются виртуальной клавиатурой.

### 5.2. Дизайн-система

- Единые токены цвета, типографики, отступов, радиусов и теней; никаких случайных значений.
- Переиспользуемые компоненты кнопок, полей, карточек, статусов, диалогов и уведомлений.
- Не более двух семейств шрифтов; иконки — из одного набора.
- Для всех интерактивных элементов обязательны состояния наведения, фокуса, нажатия и отключения.
- Тёмная тема включается только при покрытии всех состояний и экранов; иначе не реализуется.

### 5.3. Состояния и обратная связь

- Использовать общие компоненты загрузки, пустого состояния, ошибки и успеха; локальные вариации запрещены.
- Состояние загрузки выбирается до запроса, а не после пустого рендера.
- Ошибка не очищает введённые данные; повторная попытка использует то же содержимое формы.
- Защита от двойной отправки реализуется и на клиенте, и на сервере.
- Необратимые действия требуют подтверждения.
- После изменения данных обновлять серверное состояние; оптимистичное обновление допустимо только с корректным откатом.

### 5.4. Доступность: проверки

- Контраст проверяется по токенам и через axe/Lighthouse, а не на глаз.
- Перед сдачей: полный проход клавиатурой, видимый фокус, ловушка фокуса в диалогах, закрытие по Escape.
- Семантические элементы и подписи полей обязательны; статусы компонуются с текстовой подписью, а не только с цветом.
- Базовая проверка скринридером ключевых экранов.
- Учитывать `prefers-reduced-motion` и масштабирование интерфейса.

### 5.5. Производительность: бюджеты

- LCP ключевых экранов — не более 2,5 с на мобильном соединении.
- Начальный клиентский JS маршрута — в разумном бюджете; превышение обосновывается и проверяется на сборке.
- CLS — не более 0,1: у изображений и шрифтов заданы размеры, используется `font-display: swap`.
- Изображения — современные форматы, адаптивные размеры, ленивая загрузка вне первого экрана.
- Не подключать тяжёлую библиотеку ради одной функции; проверять размер бандла после добавления зависимости.
- Отклик на действие пользователя — быстрее секунды, даже если данные ещё загружаются.

## 6. Качество кода и проверки

### 6.1. Общие правила

- TypeScript в строгом режиме. `any` и `@ts-ignore` — только с письменным обоснованием в комментарии.
- Линтер и форматтер обязательны; код должен проходить без предупреждений.
- Нет мёртвого и закомментированного кода, неиспользуемых импортов и `console.log` в production-путях.
- Нет «временных» обходов безопасности, отключённых проверок и фейковых данных, выдаваемых за реальные.
- Функции и модули имеют одну ответственность; дублирование логики запрещено.
- Публичные функции и сложные участки кратко документируются; очевидное не комментируется.

### 6.2. Ошибки и API

- Единый формат ошибок API: код, нейтральное сообщение, идентификатор запроса.
- Внутренние детали и стек не попадают пользователю.
- Ошибки логируются на сервере без персональных данных и секретов.
- На клиенте есть границы ошибок, чтобы падение одного блока не ломало страницу.
- Сетевые ошибки и таймауты обрабатываются явно.

### 6.3. Обязательные тесты

- **Юнит и интеграция (Vitest):** проверка прав доступа, RBAC-матрицы, допустимые переходы статусов заявок, Zod-схемы, расчёт сводки успеваемости, форматирование дат; интеграционные — с тестовой PostgreSQL через Prisma.
- **E2E (Playwright):** сценарии `US-01`–`US-09` на десктопе и те же сценарии на ширине 360 px; авторизация под двумя студенческими аккаунтами. `US-10` проверяется отдельным тестом безопасности, `US-11` — если включён кабинет сотрудника.
- **Безопасность:** пользователь A не читает и не изменяет ресурсы пользователя B; студент не выполняет действия сотрудника; пароли не хранятся в открытом виде; в клиентском бандле нет секретов.
- **ИИ-помощник (если включён):** инструменты не возвращают чужие данные; изменение без подтверждения запрещено; при недоступности провайдера ядро продолжает работать.
- Тесты должны быть детерминированными и не зависеть от реальной сети и внешних сервисов.

### 6.4. Команды проверки перед сдачей

Выполнить и приложить результат:

1. `prisma validate` и `prisma generate`.
2. Линтер.
3. Проверка типов (`tsc --noEmit`).
4. `vitest run`.
5. `playwright test`.
6. Сборка `next build`.
7. Проверка бандла на секреты.
8. Ручной проход сценариев `US-01`–`US-09` на 360 px.

Если какая-то проверка не запускается — это не «готово», а блокер; нужно сообщить причину.

## 7. Процесс работы и Git

### 7.1. Ветки и коммиты

- Одна задача — одна ветка с понятным именем (`feat/requests-status`, `fix/mobile-nav`).
- Коммиты небольшие, с осмысленным сообщением в формате Conventional Commits.
- Не смешивать рефакторинг, функцию и исправление в одном коммите без необходимости.
- Запрещены force-push в основную ветку и переписывание чужой истории.
- Запрещено коммитить `.env`, `node_modules`, сборки, дампы БД и секреты.

### 7.2. Работа с чужими изменениями

- Не удалять и не перезаписывать незакоммиченные файлы человека.
- Не откатывать чужие коммиты без явного указания.
- Перед разрушительной операцией (удаление файлов, сброс БД, переустановка зависимостей) — спросить.
- При конфликте интересов остановиться и описать проблему, а не выбирать молча.

### 7.3. Субагенты

- Передавать субагенту этот файл, релевантные разделы PRD, границы задачи и список файлов.
- Один субагент — одна независимая область; не давать двум агентам править одни файлы параллельно.
- Результат субагента проверяется по § 6 и § 9, а не принимается на слово.
- Субагент не расширяет scope и не принимает продуктовых решений без ссылки на PRD.

### 7.4. Документация

- Изменение продуктового поведения — сначала обновить `docs/PRD.md`, затем код.
- Архитектурное решение — новый ADR с контекстом, вариантами, выбором и последствиями. Изменение стека или мажорных версий Prisma, Better Auth, Base UI и AI SDK — только через ADR с проверкой совместимости.
- Изменение инженерного правила — обновить этот файл, не дублируя PRD.
- `docs/DEVELOPMENT_PLAN.md` обновляется при каждом изменении статуса задачи, объёма работ или текущего фокуса. Отметка `[x]` без проверок запрещена.
- `docs/ai-log.md` пополняется по ходу работы: инструмент, задача, ключевой промпт, результат, ошибки и исправления. Это основа конкурсного описания процесса.
- `README.md` содержит запуск, переменные окружения, демо-аккаунты, известные ограничения.
- `docs/third-party.md` обновляется при каждом новом стороннем материале.

Формат фиксации допущения в отчёте:

> **Допущение:** … **Почему:** … **Влияние:** … **Как проверить:** …
