# План усиления «Цифрового деканата будущего»

**Дата:** 16.11.2026  
**Горизонт:** до 28.11.2026 (12 дней)  
**Статус:** исторический снимок на 16.11.2026; актуальные статусы задач — только в [`docs/DEVELOPMENT_PLAN.md`](docs/DEVELOPMENT_PLAN.md).

---

## 1. Цель

Довести прототип до состояния, в котором жюри за 10 минут проходит полный цикл:

**вход → профиль → расписание → оценки → заявка → статус → уведомление**

— на телефоне шириной 360 px, с доказуемой безопасностью, понятным ИИ-контуром и готовым пакетом сдачи.

Главный принцип: **сначала закрываем ядро и доказательства, потом добавляем «вау»**. Красивая витрина без работающих заявок и уведомлений проигрывает на критерии «имплементация».

## 3. Наши продуктовые принципы

1. **Один экран — один ответ на вопрос студента.** Не «раздел ради раздела», а «что мне делать сейчас».
2. **Действие в один-два тапа.** Заказать справку, отметить уведомление, открыть пару.
3. **Сервер — источник истины.** Права, оценки, заявки и уведомления живут на сервере; клиент только отображает.
4. **Мобильный первый.** 360 px — основной сценарий, а не уменьшенная копия десктопа.
5. **Честные состояния.** Загрузка, пусто, ошибка, успех — на каждом ядровом экране.
6. **Концепт, а не официальный сервис.** Вымышленные данные, собственная символика, заметная пометка.

## 4. Наши ключевые идеи

### 4.1. «Сегодня» — пульт дня

**Идея.** Главный экран отвечает на вопрос «что у меня сейчас и что дальше», а не перечисляет разделы.

**Что показывает:**

- текущая или следующая пара: время, аудитория, преподаватель, подгруппа;
- изменения на сегодня и завтра: перенос, отмена, замена аудитории;
- ближайший дедлайн или экзамен;
- активные заявки и их статус;
- краткая сводка успеваемости: средний балл, задолженности.

**Как делаем.** `src/lib/domain/dashboard.ts` с `getDashboard(userId, now)`; параллельные запросы через `Promise.allSettled`, чтобы сбой второстепенного блока не скрывал пару; каждая секция — отдельный компонент с пустым состоянием.

**Зачем жюри.** Это первый экран после входа; он сразу показывает, что кабинет живой и собран вокруг студента.

**Усилие:** M. **Критерии:** проработанность идеи, качество.

### 4.2. Успеваемость: понятная картина и прогноз

**Идея.** Не просто таблица оценок, а ответ «как у меня дела и что будет, если...».

**Что делаем:**

- семестры, дисциплины, формы контроля, оценки, сессия;
- средний балл, зачётные единицы, задолженности;
- прогноз красного диплома: доля «отлично», порог 75%, вердикт;
- калькулятор «а если»: что нужно получить на экзамене, чтобы выйти на цель;
- план по дисциплине: что уже закрыто, что осталось.

**Как делаем.** Чистые функции рядом с `grades-summary.ts` (`honorsForecast`, `whatIf`, `planFor`), unit-тесты на границы: 0/3/5 оценок, тройка, долг, недостижимый автомат. Если меняем продуктовое поведение — сначала PRD и spec p3.

**Зачем жюри.** Превращает сырые оценки в понятный студенту ответ; дешёвый «вау» без новых таблиц.

**Усилие:** S/M. **Критерии:** проработанность идеи, качество.

### 4.3. Заявки как доставка

**Идея.** Студент видит не «заявка создана», а трекер: **Новая → В работе → Готова**, с датами, комментарием и сроком.

**Что делаем:**

- 3–4 типа на старте: справка об обучении, выписка из приказа, пересдача, практика;
- мастер по цели: «для чего нужна справка» → нужный тип и поля;
- форма на React Hook Form + Zod;
- создание в `prisma.$transaction`: номер, событие, уведомление;
- список и карточка только владельца; чужой id → 404;
- история статусов, отмена из «Новая», `dueDate`, место получения;
- сид с историей статусов, а не только с одной записью.

**Как делаем.** Спецификация p4 — контракт до UI; `Request`, `RequestEvent`, enum статусов; Server Actions с `requireUser` первой строкой, Zod на сервере, `revalidatePath`.

**Зачем жюри.** Это половина продукта и главный сценарий, который проверяют руками: «подал — увидел статус».

**Усилие:** M. **Критерии:** проработанность идеи, имплементация.

### 4.4. Справка с QR-проверкой

**Идея.** Результат заявки — не серая плашка, а документ, который можно показать.

**Что делаем:**

- печатный HTML-бланк с `@media print` и водяным знаком «КОНЦЕПТ · НЕ ОФИЦИАЛЬНЫЙ ДОКУМЕНТ»;
- QR-код на публичную страницу проверки;
- `verifyCode` (96 бит, не связан с id заявки);
- `/verify/[code]` без сессии отдаёт только минимум: ФИО, факультет, направление, курс, группа, дата, статус;
- **без** номера зачётки, оценок, логина и других лишних данных;
- PDF — позже, после HTML; только через ADR и лёгкий генератор.

**Зачем жюри.** Сильный демонстрационный момент и одновременно проверка приватности: публичная страница показывает, что мы умеем не раскрывать лишнее.

**Усилие:** M. **Критерии:** проработанность идеи, имплементация, безопасность.

### 4.5. Уведомления, связанные с действиями

**Идея.** Уведомление — не отдельная лента «ни о чём», а следствие события: заявка сменила статус, приближается дедлайн, изменилась пара.

**Что делаем:**

- модель `Notification` со ссылкой на объект и `readAt`;
- создание в той же транзакции, что и смена статуса заявки;
- колокольчик с числом непрочитанных в шапке и нижней навигации;
- страница: фильтр «все / непрочитанные», отметка «прочитано», переход к объекту;
- e2e: смена статуса → уведомление → «прочитано».

**Как делаем.** Спецификация p5; чистый маппинг «статус → текст уведомления»; Server Action для `markRead` с проверкой владельца.

**Усилие:** S/M. **Критерии:** связность, имплементация.

### 4.6. Кабинет сотрудника: очередь и брифинг

**Идея.** Второй ролевой сценарий: студент подал — деканат обработал — студент увидел. Это сильнее, чем ещё один студенческий раздел.

**Что делаем:**

- роль `DEAN_EMPLOYEE` уже есть в модели;
- `/staff/requests` — очередь с фильтрами-счётчиками: все / новые / в работе / готовы / отклонены;
- карточка заявки: данные, история, комментарий, смена статуса;
- переходы только из разрешённого списка, в транзакции, с событием и уведомлением студенту;
- «утренний брифинг»: просроченные, новые за сутки, ближайшие дедлайны;
- студент на staff-маршруте → редирект/404; staff-действия недоступны студенту.

**Зачем жюри.** Полный цикл выглядит как настоящий сервис, а не как макет.

**Усилие:** M/L. **Критерии:** проработанность идеи, имплементация.

### 4.7. Помощник с реестром действий

**Идея.** Помощник — не чат сбоку, а управляемый контур: он понимает намерение, предлагает действие, студент подтверждает, сервер выполняет и пишет аудит.

**Что делаем:**

- `src/lib/actions/registry.ts`: `defineAction({ name, schema, risk, roles, summary })` — список действий, безопасный для клиента и промпта;
- `src/lib/actions/handlers.ts` с `import "server-only"`: реализации, первый аргумент — `viewer` из `requireUser`, **не** `userId` из аргументов;
- `ActionLog` и `PendingAction` в Prisma; журнал «что делал помощник»;
- `runAction(name, args)` для UI и `confirmAction(pendingId)`; без подтверждения БД не меняется;
- откат для обратимых действий;
- детерминированный парсер 25–35 фраз: расписание, оценки, заявки, уведомления, «что если»;
- опциональный LLM только на сервере, по env-ключу, с rate limit; нет ключа — честный быстрый режим;
- eval-тесты фраз и тест prompt injection: текст заявки остаётся данными, не инструкцией.

**Зачем жюри.** Это закрывает критерий «нейротехнологии» не словом «подключили модель», а архитектурой: реестр, подтверждение, откат, аудит, fallback, тесты.

**Усилие:** M/L. **Критерии:** нейротехнологии, безопасность.

### 4.8. Расписание в календаре телефона

**Идея.** Студент не должен вручную переносить пары — расписание подписывается в календаре.

**Что делаем:**

- `/api/schedule.ics` — только своё расписание по сессии;
- `/api/calendar/[token]` — подписка по HMAC-токену, без cookie;
- корректный `fold` 75 байт, escape `,;\n`, `DTSTART;TZID=Europe/Moscow`, `UID` и `SEQUENCE` для переносов;
- отменённая пара — `STATUS:CANCELLED`, а не тихое исчезновение;
- ссылка и короткая инструкция для iPhone/Android.

**Усилие:** S. **Критерии:** качество, мобильность.

### 4.9. «Мой деканат»: люди, кабинеты, часы

**Идея.** Студент понимает, куда идти и к кому, без звонка и очереди.

**Что делаем:**

- модель `DeanContact`: должность, зона ответственности, кабинет, часы приёма, телефон (вымышленные);
- сид 5–7 человек;
- карточка в профиле или заявках: «Справки — каб. 214, пн–пт 10:00–17:00»;
- блок «кто за что отвечает».

**Усилие:** S. **Критерии:** проработанность идеи, реализм.

### 4.10. Демо-сценарии и аккаунты

**Идея.** Жюри не должно тратить время на ввод паролей и поиск нужного состояния.

**Что делаем:**

- 2 студента с заметно разными профилями: отличник и студент с долгом;
- при наличии staff-кабинета — сотрудник;
- на `/login` — компактный блок демо-доступа и 5–6 сценариев проверки;
- сброс демо-данных одной командой;
- пароли — только в README/описании, не в коде и не в клиентском бандле.

**Усилие:** S/M. **Критерии:** имплементация, удобство для жюри.

## 8. Безопасность и качество: наши правила

### 8.1. Доступ к данным

- Отдельный серверный модуль доступа; scope-функции возвращают `Prisma.WhereInput`.
- Сентинел `NOTHING` для заведомо запрещённого запроса.
- Правило: **id + scope → выборка**; чужой объект = 404, не 403.
- `findOwnedOrNotFound` для профиля, заявки, уведомления, оценки, занятия.
- Каждый новый маршрут с id получает тест на чужой id.

### 8.2. Server Actions

- `requireUser`/`requireStudent`/`requireStaff` первой строкой.
- `userId`/`studentId` — только из сессии, никогда из аргументов.
- Zod-схема на сервере; та же схема в форме.
- Изменения статусов — в `prisma.$transaction` с проверкой допустимого перехода.
- Защита от двойной отправки на клиенте и сервере.

### 8.3. Заголовки и секреты

- CSP, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, защита от кликджекинга.
- Better Auth остаётся единственной auth-системой; cookie `HttpOnly`, `Secure`, `SameSite=Lax`.
- `DATABASE_URL`, `BETTER_AUTH_SECRET`, ключ LLM — только на сервере.
- Тест: в HTML и `.next/static` нет секретов и паролей сида.

### 8.4. Качество интерфейса

- Загрузка, пусто, ошибка, успех — на каждом ядровом экране.
- Скелетоны по сетке, ошибка без стека, «Повторить» с сохранением введённых данных.
- Контраст токенов WCAG AA, axe, клавиатура, видимый фокус, Escape в диалогах.
- 360/390/768/1280 px; отсутствие горизонтального скролла; 200% масштаб.
- `prefers-reduced-motion`; анимации только для обратной связи.
- Только вымышленные данные; водяной знак «КОНЦЕПТ» на документах.

### 8.5. Зависимости и архитектура

- Новая зависимость — только через ADR: лицензия, размер, альтернатива.
- Тяжёлый PDF-стек — не тащим; начинаем с HTML-печати.
- WebLLM, Web Push, кастомный service worker — только при наличии времени и тестов.
- Никаких персональных данных в `localStorage`; личные страницы не кэшируем.
- Один источник статуса задач — `docs/DEVELOPMENT_PLAN.md`; новые задачи с новым ID.
